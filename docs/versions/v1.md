# v1 — the (k, cause) scorer

## What it is

The current (and, so far, only) learned scorer. Built on the shared
pipeline and feature vector described in the README: given a board state
and a candidate clue, predicts a distribution over how a turn using that
clue would play out, which a separate closed-form calculation turns into
an expected reward for every possible announced number.

- **Output**: a 13-way distribution over `(k, cause)` — `k` is how many
  own-words a guesser reveals in a row before stopping (0..3), crossed with
  `cause`, which role actually stopped it (neutral / opponent / assassin),
  plus one right-censored class for `k=4` (hit the cap, no miss, cause
  undefined). Naming it "cause" and not just "k" is the model's central
  idea: a stop on an opponent word and a stop on the assassin are very
  different outcomes, and this model is built to actually tell them apart
  instead of collapsing every non-own-word stop into a single "miss"
  label. `codenames/scorer.py::outcome_class`/`decode_outcome_class`
  pack/unpack this.
- **Scoring**: `codenames/scorer.py::reward_matrix`/
  `expected_reward_and_best_n` take four independent reward parameters —
  `own_reward`, `neutral_reward`, `opponent_reward`, `assassin_reward` —
  instead of a single flat penalty. A natural-stop cell charges the
  *cause's own* value; defaults are the real game's own +1 / neutral −0.2 /
  opponent −1 / assassin −10 (neutral was revised from 0 to −0.2 after
  the numbers below were generated — see docs/log.md — since a neutral
  guess still burns a turn for no progress and shouldn't be free), not
  the separate untuned −0.3-for-neutral constant
  `codemasters/linear_scorer.py`'s hand-coded baseline uses. None
  of the four are baked into training: turning any of them down at play
  time requires no retraining, because the model only ever learns the
  empirical `(k, cause)` outcome, never a specific reward value.
- **Attempts rule**: a clue announcing `n` gets exactly `n` guesses, not
  the standard Codenames `n+1`-with-bonus-guess rule. See `docs/log.md`'s
  numbering-convention entries.

## Trained variants

Six checkpoints, one per guesser-pool noise level, all sharing this
architecture (`cache/m9/checkpoints/noise_*/`, auto-discovered by
`scripts/web_inspector.py`):

| noise_std | val_loss | val_accuracy |
|---|---|---|
| 0.0  | 0.8507 | 0.6810 |
| 0.03 | 0.9766 | 0.6350 |
| 0.06 | 1.1788 | 0.5704 |
| 0.08 | 1.3017 | 0.5358 |
| 0.1  | 1.4123 | 0.5024 |
| 0.15 | 1.6228 | 0.4332 |

**Read val_loss/val_accuracy as "how predictable is this noise level's
task," not "how good is this model."** Lower noise makes the guesser
pool's behavior closer to deterministic, which mechanically lowers the
achievable loss/accuracy at the Bayes-optimal solution — these numbers are
not comparable to a measure of actual play quality across noise levels
(anecdotally, in-UI clue quality seemed to peak around 0.06-0.08, not the
lowest-loss 0.0/0.03). The right comparison for "which noise level plays
best" is real game outcomes via `codenames/arena.py`, not this table — see
the self-play results below for the 0.08 level; the other five haven't
been run through the arena yet.

Regenerating/retraining any of these is cache-aware:
`scripts/run_ablation_study.py --noise-levels "<comma-separated>" --noise-only`
skips both generation and training for any level whose data/checkpoint
already exists on disk, so adding one new level only pays for that level.

## Self-play evaluation (noise_std=0.08)

**Superseded as the project's headline numbers** (per user direction:
everything should be evaluated with both teams actually playing against
each other, not one team against static distractors) **by the real
two-team self-play numbers in "Open questions for the next version" →
item 2 below**, and in the README. This section is kept as-is, historical
record of the single-team methodology used through the middle of this
project and how `learned:noise_0_08` performed under it — useful for
understanding what changed and why, not as a number to cite as current.

Full games (`codenames/game.py::play_game`, not just single-turn scoring),
`learned:noise_0_08` as codemaster against each of that same noise level's
3 guessers in turn (`codenames/arena.py::run_arena`), 300 seeded boards per
guesser, 900 games total. **Rerun** after `ROLE_REWARD[Role.NEUTRAL]`
changed from 0.0 to -0.2 (see `docs/log.md`) -- the numbers below reflect
the current default; the original run under `neutral_reward=0.0` isn't
kept since only the reward table changed, not the model or the pool.

**Win rate deliberately isn't reported as its own headline number.** Every
game here ended in either a win or an assassin hit (0 timeouts against
`DEFAULT_MAX_TURNS=40`), so win rate is always exactly `1 - assassin-hit
rate` -- reporting both would just be the same number twice, and win rate
alone can't distinguish "plays it extremely safe" from "actually finds
its own words efficiently." The per-guess breakdown and the turns split
below are the more informative numbers:

| | value |
|---|---|
| assassin-hit rate | 4.0% |
| mean game length (all games) | 6.54 turns |
| mean game length (wins only) | 6.66 turns |

The two turn-length figures answer different questions on purpose: "all
games" blends in games that end abruptly on an early assassin hit, so it
understates how long a *successful* game actually runs -- "wins only" is
the fairer answer to "how many turns does it typically take to clear the
board." (`mean_turns_on_win` is `None` when a codemaster/guesser pair has
zero wins to average -- see `codenames/arena.py::CrossPlayResult`.)

Per-guess role breakdown (of every individual word actually guessed across
all 900 games, not per-game):

| own | opponent | neutral | assassin |
|---|---|---|---|
| 86.6% | 6.2% | 6.9% | 0.4% |

**Against the fixed baselines**, same setup, 900 games each:

| codemaster | assassin-hit | turns (all) | turns (wins only) | own | opponent | neutral | assassin |
|---|---|---|---|---|---|---|---|
| **model 1 (learned)** | **4.0%** | **6.54** | **6.66** | **86.6%** | **6.2%** | **6.9%** | **0.4%** |
| centroid | 12.2% | 7.69 | 8.17 | 82.9% | 8.9% | 7.0% | 1.2% |
| linear_scorer | 26.7% | 19.45 | 19.81 | 39.7% | 31.1% | 27.9% | 1.3% |
| random | 89.4% | 9.89 | 15.81 | 35.4% | 30.9% | 26.9% | 6.8% |

`centroid` and `random` don't read the reward table at all
(`CentroidCodemaster` picks by pure similarity, `RandomCodemaster` by
neither), so their numbers here are just run-to-run `NoisyGuesser` RNG
noise relative to the pre-rerun figures, not a real behavior change; only
`linear_scorer` and `learned` actually score against reward values, and
only `learned`'s come from the changed default (`linear_scorer` uses its
own separate hardcoded -0.3-for-neutral constant, unaffected).

Worth reading these together, not each column in isolation: `centroid`'s
per-guess breakdown (82.9% own) is now clearly behind model 1's (86.6%),
and its assassin-hit rate is still 3x higher -- worse at finding own
words *and* worse at avoiding the one guess that ends the game outright.
`linear_scorer` and `random` both guess own-words less than half as often
as model 1 or centroid. `random`'s two turn-length figures diverge
sharply (9.89 all games vs. 15.81 wins-only, more than half again) --
its rare wins take much longer than its typical (early-assassin-ending)
game, unlike model 1's, which stay close together (6.54 vs. 6.66).

`codenames/arena.py::CrossPlayResult` reports the per-guess role rates
and the turns split for any codemaster/guesser pair --
`scripts/run_arena.py`'s output includes them automatically.

This run used `codenames/gpu_arena.py`'s batched GPU path (the default),
166.3s for all 12 codemaster x guesser pairs, 300 boards each -- an
earlier run of the same setup on the plain CPU arena took 716.4s for just
the "learned" rows (13.05x, see docs/log.md). Any future bulk self-play
evaluation of this model should use the GPU path
(`scripts/run_arena.py`'s default).

## What's built on top of this model

All in `scripts/web_inspector.py` / `scripts/webui/inspector.html`, all
adjustable per-request with no retraining:

- The four reward values above, as UI fields.
- A play-time guesser-noise dial (one of the six trained levels) for the
  turn-simulation panel — independent of which noise level the codemaster
  itself was trained under, so a train/test mismatch can be explored
  directly.
- A clue-rarity filter (`CLUE_RARITY_PERCENTILE`, derived from GloVe's own
  frequency-ordered vocabulary file, no new dependency) that screens
  obscure candidate clues out of the ranked results.

## Open questions for the next version

1. **Cross-turn clue memory -- built and evaluated: a real negative
   result.** Done as suggested above:
   `codenames/guessers/history_aware.py::HistoryAwareGuesser` wraps any
   base guesser and can claim one earned bonus guess per turn (real
   Codenames' `n+1` rule, reinstated only when there's an actual reason
   to use it -- see `codenames/guessers/base.py`'s module docstring) to
   chase a word a past clue's miss plausibly left unaccounted-for. No
   codemaster or training changes needed, exactly as scoped.
   - Comparing different clues' raw similarity scores to decide which
     backlog word is most worth the bonus doesn't work -- checked
     empirically (docs/log.md), a clue's *typical* similarity to the
     board vocabulary correlates strongly with how common the word is
     (r=0.84 for GloVe -- the "hubness" effect in cosine-similarity
     spaces), so a generic-sounding old clue would systematically
     outrank a genuinely strong candidate under a rarer new clue if
     compared on a raw scale. Fixed by z-scoring each clue's scores
     against its own similarity distribution over the board vocabulary
     before any cross-clue comparison.
   - Evaluated in real two-team self-play (300 boards each,
     GPU-batched, both models' checkpoints against their own guesser
     with vs. without history-awareness): assassin-hit rate goes from
     0.0% to 7.3% for model 1 (`noisy_glove` → `history_aware_noisy_glove`)
     and from 5.0% to 7.3% for model 1.1 (`blend` → `history_aware_blend`),
     with own-word rate dropping in both cases too (97.4%→85.2%,
     86.9%→83.8%). This confirms an earlier single-team-arena finding
     (docs/log.md): the bonus guess fires on a meaningful fraction of
     turns but lands on "own" far less reliably than an ordinary guess,
     and its assassin-hit rate specifically is markedly higher than the
     guesser's normal rate. **Not adopted** -- kept in the codebase as a
     documented, honestly-reported negative result (see README), not a
     recommended guesser.
2. **Optimizing win probability instead of expected reward**, including
   score-differential-aware risk (play safer when ahead, riskier when
   behind) and modeling how revealing a word changes the *opponent's*
   available clues. Both need something this project didn't model until
   recently: an actual second team taking its own turns. That
   infrastructure now exists —
   `codenames/game.py::play_two_team_game`/`codenames/board.py::OpponentBoardView`
   (see `docs/log.md`), built for the web UI's "Full Game" tab and every
   codemaster/guesser/scorer unchanged, `LearnedCodemaster` included.
   (`LearnedCodemaster` briefly couldn't play the 8-card side — its
   feature vector's fixed 9-own/8-opponent slot layout would overflow
   under `OpponentBoardView`'s swap. First fixed with a `play_two_team_game`
   pre-reveal step, then corrected again after user pushback: that step
   silently changed team A's true win condition (9 words needed → 8), a
   real rule change, not a free workaround. The actual fix:
   `codenames/features.py` now keeps its own `FEATURE_SLOT_COUNTS`
   (own=9, opponent=9), decoupled from `codenames/board.py::ROLE_COUNTS`
   (the real board's card counts, still 9/8/7/1, unchanged) — the vector's
   slot width just needs to be wide enough for any real perspective,
   independent of how many cards actually get dealt. No rule changes, no
   pre-reveal needed. Real cost: this widens the model's input dimension,
   so every existing `LearnedCodemaster` checkpoint needed retraining
   before it worked again at all (single-team included); no baseline
   codemaster is affected. A second, separate gap was caught before that
   retrain would have been wasted: retraining alone would only teach the
   model to accept the wider input, not to interpret it correctly — every
   training example was generated from `Board.generate()`'s real
   perspective directly, so the new 9th opponent slot was always
   mask=0/padding in training, never once populated with a real value.
   Fixed in `scripts/generate_training_data.py`: half of all examples
   (`SWAP_PERSPECTIVE_PROB`, "team A is just as important as team B") are
   now built from `OpponentBoardView`'s swapped perspective instead,
   which the entire generation pipeline accepts as a drop-in substitute
   for the same reason a codemaster or guesser does. All 6 checkpoints
   (5 noise levels + blend) were regenerated and retrained against this
   corrected data. See `docs/log.md`.) `score_differential` in the current
   feature vector is still own-progress-minus-own-mistakes, not a race
   against anything, so it doesn't yet support "ahead/behind" in the
   sense this idea needs, and the arena/self-play evaluation machinery
   (`codenames/arena.py`, `codenames/gpu_arena.py`) is still
   single-team-only (`codenames/two_team_arena.py` now exists for bulk
   two-team *self-play*, including the same learned codemaster on both
   sides). Turning any of this into training data or a feature vector
   that works from either team's perspective is a genuine scope
   expansion, not a small tweak — see `docs/design-decisions.md` before
   starting it.

   Real two-team self-play numbers, `learned:noise_0.08` + `noisy_glove`
   on both sides, 300 boards, real 9-vs-8 rules, retrained checkpoint
   (both perspectives represented in training data): **assassin-hit rate
   0.0%**, 9.03 half-turns/game (9.03 for clean finishes — every game
   ended cleanly), per-guess breakdown own 97.4% / opponent 0.3% /
   neutral 2.3% / assassin 0.0%. This supersedes the one earlier run of
   this comparison (assassin-hit 0.3%, 8.07 half-turns, own 95.4%),
   which used the now-abandoned pre-reveal fix — team A's true target
   was silently 8 words there, not 9, so it isn't representative of the
   real game and shouldn't be used as a baseline for future comparisons.
   For context, an earlier smoke test against a `centroid`-codemaster
   opponent (real 9-vs-8 rules throughout) put the assassin-hit rate at
   10.0% — real two-team play against a weaker, noisier opponent is
   clearly riskier than facing the same learned strategy on both sides.

   Two-team self-play numbers for every baseline codemaster (real 9-vs-8
   rules throughout, no pre-reveal — these were never affected by the
   feature-vector issue), 200 boards each, `noisy_glove` on both sides:

   | codemaster      | assassin-hit rate | half-turns (all) | half-turns (clean) | own / opp / neutral / assassin |
   |-----------------|-------------------:|------------------:|---------------------:|---------------------------------|
   | random          | 85.5%              | 9.71              | 15.48                | 33.6% / 32.0% / 27.7% / 6.7%    |
   | oracle          | 56.0%              | 5.89              | 7.57                  | 58.7% / 17.8% / 19.3% / 4.2%    |
   | centroid        | 15.5%              | 10.20             | 11.04                 | 90.0% / 3.8% / 5.1% / 1.0%      |
   | linear_scorer   | 4.5%               | 18.71             | 18.71                 | 41.8% / 30.1% / 27.9% / 0.2%    |

   `linear_scorer`'s very low assassin rate comes with a real cost:
   18.71 half-turns/game (vs. centroid's 10.2), meaning it's slow and
   overly conservative rather than genuinely skilled — it rarely finishes
   cleanly at all, so "clean finish" and "all games" coincide. `oracle`'s
   perfect single-space foresight doesn't generalize to a noisy guesser
   pool, hence a surprisingly high assassin rate despite a low turn count.
   `centroid` remains the strongest non-learned baseline by this metric.
   This confirms `play_two_team_game`/`two_team_arena.py` are genuinely
   codemaster-agnostic in practice, not just by inspection — every
   baseline ran without any code changes beyond adding `oracle` to
   `scripts/run_two_team_arena.py`'s CLI choices (`OracleCodemaster` was
   simply missing from that list, not blocked by anything architectural).

   All the numbers above evaluate against a single fixed guesser
   (`noisy_glove`), which is narrower than the 3-guesser, equally-weighted
   distribution the model was actually trained against. The README now
   reports the current standard instead: each game's guesser drawn
   uniformly from all 3 (`codenames/two_team_arena.py::MIXED_GUESSER`),
   plus two additional stats (mean announced clue number, mean correct
   guesses per clue). See the README for those numbers.

A smaller, compatible-with-today's-scope version of the risk-adjustment
idea is cheap to try first: make `assassin_reward` a function of
`board.remaining(Role.OWN)` instead of a constant (e.g. more risk-tolerant
once few own words remain) — no second team required, no retraining, just
a policy change in `LearnedCodemaster`.
